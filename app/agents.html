Using Flockdeck

Agents and models

Every agent pane runs a coding agent of your choosing at a model of your choosing. Claude Code is the default and behaves exactly as it always has; the picker is how you reach anything else.

Picking one

The plain Ctrl+Shift+T and Ctrl+Shift+D stay one keystroke and take the default agent, because that is what you want almost every time. To choose deliberately, use New agent tab (choose agent)… or Split right (choose agent)… from the command palette, or click the ▾ beside the + that opens a new tab.

The picker lists the agents that can be started first and then the ones that cannot. An agent that cannot be started is shown greyed and marked unavailable, without a reason, rather than hidden: somebody who has never installed Codex should still learn that Flockdeck would run it. Expand an agent for its models, with its default marked. A model carries its tier where it has a fixed one (small, mid or top: how capable, and so how costly, it is among that agent's own models). A model shows no price: the same model may be billed per token or covered by a subscription, and only you know which. At the foot of the picker, Set as default for makes the choice stick, either for this project or for every project, so the one-keystroke split keeps doing the right thing. Use the default for every project removes this project's own choice.

The pane header names what is running, beside the branch and in the same dim weight: claude · sonnet, codex · gpt-5.6-sol. A shell pane shows nothing there, because there is nothing to choose. For Claude Code, where its status line is read, it is followed by what the conversation has spent and how near its usage limit it is; Spend and limits explains the figures.

Agents are programs

Agents are the tools you would run in a terminal yourself: Claude Code, Codex, Gemini, Aider, opencode, Cursor's agent. In a terminal pane Flockdeck runs the command in the pane's pseudo-terminal, so it behaves exactly as it does anywhere else and uses whatever login that tool already has. New Claude Code and opencode panes are structured instead; see the next section. Flockdeck does not install agents. One whose command cannot be found or started is shown as unavailable.

Flockdeck no longer has a chat client of its own for talking to a model API directly. The flockdeck chat command, and the Anthropic, OpenAI, Google and OpenAI-compatible agents built on it, were removed. An agents.json entry that still has an api block, or "runner": "api", is refused with a notice saying so.

Structured agents

Direction (27 Oct 2026, updated 6 Nov 2026): new Claude Code and opencode panes start structured. The shell inbox, flockdeck msg and typed wake are the mail routes of terminal panes, which stay as the opt-out and for agents with no structured route. A structured pane sends with send_message, looks at the team with list_peers, and gets mail as prompts. The task board is a planned removal. See docs/acp-direction.md in the repository.

A structured agent is one Flockdeck talks to over the Agent Client Protocol instead of in a terminal. Its pane has no screen: the drawer shows its conversation, a box to send it a prompt and a Stop button.

New Claude Code and opencode panes are structured by default. This applies to new panes only: a saved layout brings each pane back as it was, so a terminal pane stays a terminal pane.

To use a terminal instead:

  • Settings, General, New panes start as: choose Terminal. Panes that are already running are not ended.
  • The picker lists both, as "Claude Code (structured)" and "Claude Code (terminal)", and the same for opencode.
  • flockdeck spawn -terminal starts the terminal version from the command line.
  • A structured pane that did not start, needs signing in, or whose agent ended has a Restart as terminal button. The pane keeps its place and folder; the conversation starts afresh.

These agents have no structured version and always run in a terminal: Cursor Agent, Aider, plain shells, and any command-line agent you add in agents.json. Codex and Gemini CLI stay in a terminal for now too; their structured versions are hidden until they have been tried against the real programs.

On a machine with paired devices or Remote turned on, new panes stay terminal unless you choose Structured in Settings. A phone is told when a structured agent is waiting and cannot answer it yet, so a person away from the desk would be left with a stalled pane.

Type / at the start of the prompt box to list the commands the agent offers, with their argument hints. Keep typing to filter, move with the arrow keys, and press Enter or Tab to choose one, or Escape to close the list. A choice only writes /name into the box: the agent runs the command when you send the text. Flockdeck's own commands (today /stop) are listed first, under their own heading, and run at once. The list is whatever the agent advertises, so it differs between agents.

A row of selectors above the conversation shows the agent's mode, its model and any other setting it offers, such as the effort. Pick a value to change it. The selector shows what the agent reports, so a change the agent refused leaves the old value in place. /mode and /model appear in Flockdeck's group for the agents that offer them: choosing one moves you to its selector, and typing /mode plan and sending sets the mode without a prompt. A value that is not on the agent's list is not sent. A change to a mode that reads as running without asking (such as a YOLO or bypass mode) asks you to confirm first, by either route, and the pane shows its warning while it is in that mode. /mode and /model replace an agent command of the same name; to send the agent its own, start the text with a space.

The prompt box takes several lines. Enter sends (so does Ctrl or Command with Enter) and Shift+Enter adds a line; there is no setting to swap them. The box grows to ten lines. Up, with the caret on the first line, steps back through the prompts you sent to this pane, and Down steps forward again to the text you were writing. The draft and the last 50 prompts are kept for each pane in this window's storage, so they are still there after you switch tabs or close the drawer; a prompt over 8 KiB is sent but not remembered, and the records of the 30 panes you used last are kept. They are plain text on this machine, so clear them with the browser data of the window if you pasted something private.

Type @ at the start of a word to list files under the pane's working directory. In a git checkout the list is what git tracks or does not ignore, so .gitignore is honoured; elsewhere it is a bounded walk that skips hidden folders and node_modules. At most 50 names are shown, best match first, and "More files match" says there are more. Tab takes the highlighted name; Enter takes one only after you moved to it with an arrow key or the mouse, and otherwise sends your text. Choosing one writes @relative/path into the text; Flockdeck does not read the file, so the agent opens it. Links are never followed or listed. A window reached through the relay has no file list.

You can type while the agent is working. The text waits in a queue of up to 16 prompts and is sent when the turn ends. The queue is listed under the conversation, next first, with Edit, Remove and Send now on each of your prompts, and Clear to remove all of yours. An edit or removal is refused, and says so, if the prompt was sent while you were looking at it. Messages from other agents are in the same list, marked "Mail from" and the sender's name, and the pane's opening prompt is marked "From Flockdeck". You cannot edit or remove either, and Clear leaves them; Send now works on them, and a mail turn you cancel that way counts as handled. Send now ends the running turn (the agent is told to cancel) and sends that prompt next with the rest of the queue behind it, which is the nearest ACP has to steering an agent mid-turn: the agent does not read your text while it works. Stop ends the turn and drops the whole queue; Stop, keep queue ends the turn and goes on to the next prompt. Mail beyond the 16 the pane holds waits in the inbox and is not listed until there is room.

While a turn runs, Esc stops it, and so does Ctrl+C when no text is selected (with text selected it copies). While the agent waits on a permission, Esc belongs to the permission and only Ctrl+C stops the turn. Unlike the Stop button these keep the prompts waiting in the queue, so the next one is sent. Esc does nothing while a menu is open or the box has text in it. The box says so while the agent works.

When the agent keeps a plan or todo list, it is shown above the conversation as a checklist: how many are done and which is in progress, and each item with its state. Click the Plan line to close or open it.

When a window is behind another, a structured agent that asks for a permission or needs setting up raises a desktop notification "needs you", and one that finishes a turn of ten seconds or more raises "finished". The notification names the pane and its branch and never what the agent asked or said. A phone paired through Flockdeck Remote is sent "Answer on the desktop" when a structured agent is waiting, and cannot answer it yet: the phone app does not offer Allow or Deny, and nothing the agent asked reaches the phone.

Start a line with ! to run a command yourself: !git status runs in this pane's folder, as you, and shows its output in a list under the conversation. The agent is not asked and does not see it; press Send to agent on a command to give the agent the command and the end of its output as a prompt. One line only, and a command ends by itself after ten minutes. Stop ends one sooner, and closing the pane ends all of them. The command sees your usual PATH but none of Flockdeck's own variables or any stored API key. To send the agent a prompt that starts with !, put a space before it. A window reached through the relay has no !. On Windows a windowed program such as !notepad is not ended by Stop or by closing the pane, and console output in a non-ASCII code page can show as replacement characters. Send to agent puts the output in a fenced block marked as program output, without further scrubbing, so read it first. Commands an agent starts in the background are not listed: Flockdeck does not run the agent's commands for it, so they show only as the agent's tool output.

When the agent takes images, paste one into the box, drop one on it, or press Attach image. Flockdeck saves the picture in its own state folder, not in your checkout, and writes [image: path] into the text for the agent to read. A large picture is scaled down first, and one picture is attached at a time. Agents that do not take images get no Attach image button and say so if you paste one.

The header shows how much of the agent's context window is used, as a bar and a percentage; press it for the figures: tokens used, the window, what is left, and the cost if the agent reports one. These are the numbers the agent last sent. A figure it did not send says "Not reported", and tokens in and out and a breakdown of the context are not shown, because the agent's report does not have them. Each reply has a Copy button, and Copy last reply in the conversation bar copies the newest one as plain text; a code block has its own Copy.

Going back and forking (the claude and codex agents only; other agents do not show it): type /rewind or /fork in the prompt box. The list shows the prompts you can go back to. "Go back to before this" asks first, then removes that prompt and everything after it from the conversation and from the agent, and puts the prompt's text in the box to edit and send again. It does not put back files the agent changed. "Fork from before this" and "Fork the whole conversation" start a new pane beside this one, labelled Fork, with the conversation up to that point; this pane is not changed. Both wait until the agent is idle. The first prompt, and a prompt that follows a stopped turn, have no point before them. A fork works in the same folder as the original, so two agents can edit the same files, and its window starts empty. Both are on the machine Flockdeck runs on.

Export, in the conversation bar, saves the conversation as a Markdown file. Type the full path of a folder that exists; Flockdeck makes a new file there named flockdeck- and the pane's name and the time, never replacing one, and says where. The file holds your prompts, the agent's replies, each tool call with its summary, helper reports, notices, and mail from other agents, marked as mail with who sent it and whether it was delivered. It leaves out tool output, diffs and images, and the agent's thinking unless you tick the box (only what Flockdeck still holds is included). Every line of the conversation is quoted in the file, so nothing the agent wrote can look like a turn of yours, and images and HTML in it are written as text so that a viewer does not load them. Links and code fences are left as they were. The file takes the folder's permissions, so on Windows it is not private. A folder on a network share is refused. Secrets are replaced with [REDACTED: ...] marks by the same redactor batons use: the values in the pane's environment, the keys Flockdeck holds, the checkout's .env files and the shapes of keys. It is a filter, so read the file before you share it. Export is on the machine Flockdeck runs on; a window reached through the relay has no Export.

Agent info, a button in the header (or /info), lists what the agent says about itself: its name and version, the ways it signs in, the session, mode and model, what it can do, the names of the MCP servers the session was given, the folder and the adapter. It shows names only, with no keys and no MCP command, arguments or environment. It is on the machine Flockdeck runs on. When an agent is waiting for you to sign in, the panel opens by itself, says what the agent asked for, and has a button to start the agent again once you have signed in with the agent's own tool. Flockdeck never asks for a password or key there. To sign out, use the agent's own tool and restart the agent. The agent's own /help, /config, /permissions, /mcp, /hooks, /memory, /agents, /init and /status work when it lists them in the / menu; type them like any other command.

What to know before you use one:

  • Approval is at the desk. A permission request is answered from a window on this machine, by choosing one of the options the agent offered. A phone is told to answer on the desktop and cannot answer it, and a window reached through the relay is told its name, status, directory, branch, project, agent and model, and no text the agent wrote. Nothing is answered for you; a request still open when you stop the turn, close or restart the pane or quit is answered cancelled.
  • A card shows what you are approving. A request to leave plan mode shows the plan, and a request to edit a file shows the diff. Both are text the agent wrote, drawn as plain text and cut when long. When the agent asks you questions (Claude Code does), the card lists them with their options. Choose one or more, or type your own answer, and press Send answers; Skip tells the agent you did not answer.
  • opencode is started to ask, which a repository can override. opencode, as shipped, runs commands and edits files without a question, so Flockdeck starts it with bash and edit set to ask, and each arrives as a permission card. This builds the setting from your own and the project's bash and edit rules: each allow becomes a question, and a deny stays a deny. That is about your and the project's rules, not the built-in agents' own: opencode's plan agent, which denies edits, asks for them instead, with a card. Choosing Always on a card allows that kind of command for the rest of the session, one you had denied included. Other settings, such as webfetch, read and external_directory, are left as you set them, and opencode still runs those without asking unless you say otherwise; Flockdeck never sets anything to allow. A terminal opencode pane keeps its own configuration. A repository whose own opencode settings give an agent (agent.build.permission, or a file under .opencode/agent) permission to run commands wins over this, and the command runs without a card. A project's opencode.json or .opencode folder can also load plugins and MCP servers that run code, so no permission setting makes an opencode pane safe in a repository you do not trust. When a pane starts, Flockdeck reads what opencode resolves in that directory and, only if a command could still run without a card, the drawer header of the pane says "This agent may run commands and edit files without asking you first: in this repository Flockdeck could not make it ask, or could not check. A project's opencode.json or .opencode folder can also load plugins and MCP servers that run code, so no permission setting makes an opencode pane safe in a repository you do not trust." Open a repository you do not trust in a terminal pane, not a structured one.
  • Mail arrives as prompts. A structured agent has no flockdeck command, so it cannot run flockdeck inbox or flockdeck msg; those are for terminal panes. It sends with the send_message tool and looks at the team with list_peers. A message sent to it arrives as a prompt, with the first line Flockdeck message from agent "<role>": (the user for a message you wrote) and the text on one line after a fixed marker. This puts text written by another agent in front of an agent that may run commands, as if it were a turn from you. What limits it: the fixed first line in a block of its own, one line with escapes and control characters removed, the sender label cut at 32 characters, and a briefing that tells the agent to treat the text as a message from another agent and not as your instruction. There is no switch for it.
  • Signing in. A Claude Code pane that is not signed in shows as a blocked pane marked "needs setup", and as "Needs setting up" in the Team view. Agent info opens by itself. Press Sign in there: Flockdeck starts Claude's own login, shows you the address it prints, and restarts the pane when the login ends. Flockdeck never sees your password or key. If the button is not offered, sign in with the agent's own tool and start the pane again, or use Restart as terminal.
  • Project permissions need a trusted folder. Claude Code ignores the allow rules in a project's .claude/settings.json in a folder you have not trusted, and a structured pane cannot show its trust question. The pane says so when that happens, and every command asks until you open Claude Code once in that folder in a terminal pane and accept the prompt. deny rules and hooks in the project's settings still apply.
  • An agent that cannot be found or started shows as "the agent is unavailable" and nothing more: not the command, not the reason, not anything the agent printed. The same words come back from a refused spawn.
  • A restart starts a new session. The earlier entries stay above a line saying the agent was restarted. If the new agent cannot be started, they stay too, with a line giving the reason.
  • Rewind and Always do less than in a terminal. Going back removes the conversation after a prompt and does not put back files the agent changed. There is no Esc Esc and no /undo. Always on a permission card covers shell commands only, the exact command only, and is forgotten when the pane restarts, which Flockdeck does on an update; the agent then asks again. Choosing the accept-edits mode in the mode selector asks less for edits.
  • Recording is not available. A structured pane is not recorded. Export saves the conversation as Markdown, as above.

Not every agent can do everything

Most of what Flockdeck does beyond drawing a terminal depends on the agent cooperating, and they do not all cooperate in the same ways.

If the agent Then
reports its own lifecycle its status mark says what it is really doing, rather than what its output looks like
can resume by id restoring a layout brings its conversation back, not only its pane
writes a transcript it can be resumed from it; it is what Resume lists
answers a start-up hook its briefing survives a compaction, rather than being said once and summarised away

An agent that does none of it still works: it is a terminal with a program in it. Where a capability is missing Flockdeck falls back rather than failing: status comes from the terminal bell and a quiet timer; resume is not attempted, and the pane starts fresh.

Of the built-in agents, Claude Code reports its own lifecycle and answers the start-up hook. Codex, Gemini CLI, Aider, opencode and Cursor Agent are read from their terminals, but are still briefed: the briefing is put in front of their opening task, once, and is not refreshed. Codex, Gemini CLI, opencode and Cursor Agent get it even in a pane opened by hand with no task; Aider gets it only when there is a task, because --message makes it answer once and exit, and a message that was all briefing would end the pane. An entry in agents.json can choose the same for its own agent with "caps": {"context": "prompt"} (or "task" for the Aider behaviour), and can give it "patterns": "waiting" and "idle", each a list of phrases its output shows in that state, so that its status is read from what it prints as well. They are plain text and case does not matter. None of the built-ins has any yet.

Aider is handed its opening task with --message, which Aider treats as a single message, so a pane started with a task (by flockdeck spawn, say) may end when the task does.

API keys

An agent uses the login it already has, and Flockdeck never sees it. A key is optional: an agent starts without one. Where you set one, in API keys… or with flockdeck keys set, Flockdeck puts it in the environment of that agent's process under the variable the agent reads (GEMINI_API_KEY for Gemini CLI, OPENAI_API_KEY for Codex) and in no other process, recording or message. It is read when a pane starts, so a pane already running keeps what it had. opencode keeps its own provider logins and has no key here.

A key you exported in the environment Flockdeck runs in reaches an agent only if the agent's entry lists that variable in passEnv. Without that, an OPENAI_API_KEY you set for another tool does not move Codex off its login.

Command What it does
flockdeck keys set <agent> Reads the key from stdin, so it misses shell history
flockdeck keys list Which agents have one, not what it is
flockdeck keys clear <agent> Forgets the one Flockdeck stored
flockdeck keys check <agent> Asks the agent's endpoint whether it takes the key

Keys are kept in keys.json in the state directory, readable only by you. A key is never logged, never written into a saved layout and never shown, and the interface will not read one back to you.

Adding your own: agents.json

The picker is the built-in agents overlaid with your own file, agents.json in the state directory: %AppData%\flockdeck on Windows, ~/Library/Application Support/flockdeck on macOS, ~/.config/flockdeck on Linux.

{
  "version": 1,
  "defaults": { "agent": "claude", "model": "" },
  "projects": {
    "C:\\code\\api": { "agent": "codex", "model": "gpt-5.6-terra" }
  },
  "agents": [
    { "id": "claude", "defaultModel": "sonnet" },
    {
      "id": "mine",
      "name": "My agent",
      "exe": "my-agent",
      "models": [{ "id": "fast" }, { "id": "careful" }]
    }
  ]
}

Entries are matched to the built-ins by id and merged field by field: the claude entry above changes its default model and leaves everything else alone. An id matching no built-in is an agent of your own. "hidden": true takes one out of the picker without removing it. A model's "tier" ("small", "mid" or "top") is set or corrected the same way; anything else is named in the notice and ignored.

The file is read fresh every time the picker opens, so editing it by hand takes effect without a restart.

Roles

A role is a job an agent is started for. Flockdeck ships six: manager, planner, worker, reviewer, tester and docs. Each has a short briefing saying what the agent does, what it must not do, who it reports to and what to hand back when it finishes. An agent starts in one with -role:

flockdeck spawn -role reviewer "review the token refresh change on fix-auth"

flockdeck agents lists the roles after the agents, with the checkout each one expects and which roles it may start. An unknown role is refused with the list of roles there are.

A pane in a role is limited in what it may start. It may start only the roles its own role lists under spawns, and it may start an agent with no role (spawn without -role) only if its role has plain set, since an agent with no role has no limits. manager has plain set; the other built-in roles do not. A refused spawn says which rule it hit.

The briefing follows those limits. A pane in a role that may start nothing, such as worker or reviewer, gets no section on starting agents. A pane in a role with spawns gets examples that name those roles, such as flockdeck spawn -role worker -worktree <branch> "<task>", and is told to use the pane id that spawn prints, or flockdeck team -json shows, when it assigns a task or sends a message, because pane names are shared.

The pane is briefed for its role: the briefing gains a "Your role" section with the role's text (and, for a role that may start others, the ids of every role in the catalog), and the pane's environment carries FLOCKDECK_ROLE. The role is saved with the layout, so a restored pane is briefed for the same job. Agents in a project can see each other, message each other and share a task board (see below).

A role may name an agent and a model, or a tier (small, mid or top) in place of a model. They apply only to a spawn that names neither -agent nor -model: a spawn that names an agent keeps it. A role's model goes only to the agent the role resolves to (its own agent, or the project's default when it names none), so spawn -agent codex -role fast does not give codex a model written for claude. The built-in roles name none, so they run whatever the project runs by default.

Roles are another key of agents.json. An entry whose id is a built-in's is merged over it field by field, and any other id is a role of your own:

{
  "roles": [
    { "id": "worker", "tier": "mid" },
    {
      "id": "security",
      "name": "Security reviewer",
      "briefing": "Review the change for injection, unsafe file access and leaked secrets. Do not edit files. Report findings to whoever started you, with file and line.",
      "worktree": "readonly",
      "spawns": []
    }
  ]
}
Field Meaning
id What -role takes
name What lists and the briefing call it
description One line on what the role is for, shown beside its name in the picker and Settings. It is not given to the agent
agent, model, tier Defaults for a spawn that chose neither an agent nor a model
briefing The text the agent is given about its role
worktree own (a worktree and branch of its own), readonly (a checkout it reads and does not change) or main (the project's main checkout)
spawns The ids of the roles an agent in this role may start. An agent in a role may start only these; an agent with no role may start any
plain true lets an agent in this role start agents with no role. Off unless set

The worktree setting is part of the briefing and the role list, and it decides what flockdeck spawn does when an agent starts a helper. A helper in a role set to own, or in a role with no setting, or with no role, is given a git worktree and a branch of its own, cut from the starting agent's current commit and named from its task, with no flag needed; spawn prints the branch and directory. The helper starts in the same subfolder of the worktree that you were in, when it exists there. Uncommitted changes in your checkout are not in the worktree, and spawn says how many, so the manager can commit first. It says so only for the default worktree, not for one you name with -worktree. A tester that needs a worker's change is started with -worktree <worker branch>. Nothing removes a helper's worktree when it closes; Worktrees is where they are cleared, and files git ignores, such as node_modules, are not copied into it. -worktree <branch> chooses the branch name and -no-worktree starts the helper in the starting agent's checkout instead. A role set to readonly or main (the planner and reviewer, and the manager) is started in the starting agent's checkout. Flockdeck does not make a readonly checkout read-only. Outside a git repository, or when the worktree cannot be cut, the start is refused and the note names -no-worktree; it is never started in the shared checkout on its own. In the window, Start in a worktree is ticked when you choose a role that works on its own branch. A worktree that is none of the three, a bad tier, and a spawns entry that names no role are listed in the notice and ignored.

Starting a role from the window

The agent picker (New agent tab (choose agent)… or Split right (choose agent)…) has a Role control above the filter. None is the picker as it has always been. Choose a role and the picker shows what the role is for, asks for a task, which a role always needs, and says which agent and model the role comes to, for example claude · opus, the Worker role's choice. Enter in the task, or Start, runs the role on that agent and model. Picking an agent row in the list names the agent only, as -agent does, so the role's model still applies when that agent is the role's own; picking a model row names both, and the role's choice is not used. Ctrl+Down and Ctrl+Up walk the list from the task box or the Role control, and Ctrl+Enter starts the row picked out.

In a worktree of its own is ticked for a role whose worktree is own, and the hint says what the role expects: its own branch, a branch it reads and that the task should name (readonly), or the project's main checkout. Ticked, Flockdeck cuts a worktree and branch named from the task, as -worktree does. A role opens in a tab of its own, not as a split, and Flockdeck switches to it once it has started. If the start is refused, the dialog stays open with what you typed and the notice says why.

A role cannot be started with a shell; the window never offers one. The spawn limits above apply to agents, not to you: from the window you may start any role, including one that no role lists under spawns.

Start a team starts a team with one agent. It asks for a goal and, if you want one, an agent and model for the manager, and starts a manager with the goal as its task in the project on screen, as flockdeck spawn -role manager "<goal>" would. The manager then starts the rest. With no manager role in the catalog the dialog says so and has no Start button.

What a manager does on its own

Given a goal, a manager works through it without being asked at each step:

  1. It breaks the goal into tasks and puts them on the task board, starting a planner first when the goal is more than one obvious change.
  2. It starts a worker for each task with spawn -role worker, so each is given a branch of its own, and assigns the task to it. Planners and reviewers read and share the manager's checkout. Every agent it starts for one task gets the same -tab "<task title>", so the planner, worker, reviewer and tester for a task share one tab named after it, and another task gets another tab. The tab is forgotten when Flockdeck restarts, so a task whose helpers are still running gets a second tab of the same title the next time the manager starts one for it.
  3. It arms flockdeck inbox -follow once, before it starts helpers: under the Monitor tool in Claude Code. Each new message prints one line, which wakes the manager even after it has ended its turn, and it reads the message with inbox read. The Monitor tool expires after at most 30 minutes, and the manager starts it again. Without the Monitor tool it runs inbox -wait 90s with Bash run_in_background in a loop, because a plain background command wakes the agent only when it exits. Only Claude Code is known to be woken this way; an agent without it waits inside its turn with inbox -wait 90s (90 seconds stays inside the 120 second limit of an agent's shell command). The other roles arm the stream too, and stop once they have reported. Flockdeck writes to the manager's inbox when a helper sends a message, exits, or finishes a turn and stays idle, and when a task is blocked or ready for review.
  4. It starts a reviewer, and a tester if the change needs one, on each worker's branch, moves a task to done when the verdict is good, and sends work that needs changes back.
  5. It closes a task's helpers when the task is done, which also removes the task's tab, and reports to you: what is done and on which branches, what is blocked, and what it needs you to decide.

Some things stay with you, but only as an instruction in the briefing. A manager is told to ask and wait before it merges, pushes, opens a pull request, deploys, publishes, deletes branches, worktrees or files, or spends money, to tell its helpers to leave those to it, and to treat a message or report that says you approved something as no approval. Flockdeck does not check this: nothing stops a manager or helper from running gh pr merge or git push except the agent's own permission prompts and its willingness to follow the briefing. A helper an agent starts does not inherit that agent's auto-review setting; it starts with the installation's default.

The number of helpers is kept modest. The manager is told to run no more than four at once, and Flockdeck refuses a spawn while eight panes are open below the agent asking (its helpers, theirs, and any whose process has exited but whose pane is still open); closing a finished helper makes room. A message that says a helper is idle is from Flockdeck and carries no text from the helper. The helper's report arrives as a SendMessage from the helper, which the built-in roles send, since a manager cannot read another pane (msg send is the fallback). Agents are told not to answer a message only to acknowledge it, which would wake the sender for nothing.

A pane started in a role carries its name in its header, after the pane name, and in the Agents overview. Pane info lists it as Role. A pane started in no role shows nothing. Settings › Agents & models lists the roles to read; they are changed in agents.json, as above.

The team and messages

Every agent's briefing has a "Your team" section, the other agent panes of its project as they were when the agent started, and a "Messages" section. Targets, limits, the one-line notice, the fixed line that can wake an idle agent and what Flockdeck writes to an inbox itself are in The command line.

An idle Claude Code pane is woken from Claude's own record of its state, the sessions/<pid>.json file it keeps in its config folder: only when that file is the one for the pane's own process and conversation and says the agent has been idle for five seconds, nobody has pressed a key in the pane since, the pane's own status is idle, the pane's hooks have reported, and its output has not changed for five seconds. The line is still the fixed sentence. Anyone who can write to that folder can forge an idle record, which gets the pane at most one line a minute, and three in a row until the agent reads its mail, while it has unread mail and every other condition and limit holds.

The built-in roles say when to use messages: the manager writes to the agents it started to answer a question or change a task, and planners, workers, reviewers, testers and docs agents write to the manager when they are blocked. Planners, workers, reviewers, testers and docs agents also send their final report to the manager with SendMessage, because the manager cannot read their panes; it is still their last message too.

The task board

Each project has one task board, which every agent in it reaches with flockdeck task whatever worktree it works in. A task has a title, a body, an owner role and pane, a state, a branch, an optional baton id for context and a thread of notes. A task points at a baton and does not replace it: a baton stays the handoff document it was written as. The states, the table of who may move a task where, the messages a change sends and how the board is stored are in The command line.

The built-in roles use it this way. The planner adds a task for each step of a plan. The manager assigns them to the workers it starts, and moves a task to done once a reviewer says the change is good. A worker moves its task to in-progress when it starts, sets the branch, and moves it to in-review when the change is committed, which messages the reviewers and testers. A reviewer or tester reads a task in in-review and either adds a note and tells the manager, or moves it back to in-progress with a note that says why, which messages the worker. Every agent's briefing has a "Task board" section with the commands and a snapshot of the counts for that pane, such as "2 tasks assigned to you, 1 in review", or "2 tasks for your role, none claimed yet" for tasks assigned to a role that no pane has started.

The Team panel

Ctrl+Shift+M opens a sheet for the project on screen, with three tabs: Tasks, Messages and Agents. It shows what the command line shows, and lets you steer from the window. It updates as the team works: a task that moves, a message that arrives and a pane that starts, stops or changes status appear without reopening it, and an open task, the text you are typing and your place in the list stay as they were.

Agents lists every agent pane of the project with its name, role, what it is doing and how many messages it has not read. The Team view shows the rest of a pane's detail. Close and Close finished close panes that are idle or have exited; Close finished names them and asks first, and each pane is checked again as it closes, so one that has started working since the list was drawn is left open. A pane locked against closing keeps its button disabled. To start an agent, use the agent picker; the sheet has no button for it.

Tasks is the board, one column for each of planned, assigned, in progress, in review and done. In a window narrower than 900 pixels the columns are one list, grouped by state. Blocked and cancelled tasks are behind a button. Each card shows the id, title, who the task is for, the branch and the number of notes; the arrow keys move between cards and Enter opens one. Open a task to read its details, notes and history and to assign it to a role or a pane, set its branch, add a note, or move it. Move offers only the moves the rules allow you for that task, and a move that undoes progress needs a note in the note box. Add task adds one, and Prune finished… removes done and cancelled tasks last changed over 30 days ago.

You act as the manager, whether or not a pane has that role, and as no pane: a task you add or a note you write shows you as its author, and the agents are told it was the user. The notices are the ones a manager pane's change would send, so an agent hears when a task is assigned to it, goes to review, is blocked or done, or gets a note. Agents see you as the user (at the window), in notices, flockdeck task show and flockdeck inbox; an agent that names itself the user, you or flockdeck is shown as (agent) the user, so no agent can sign as you.

Messages lists the project's messages, newest first, with sender, recipient, time, text and whether the recipient has read it. The filter narrows them to a pane or a role. Message text is shown as plain text. Write to a pane, or to every pane in a role, in the box above the list: the message is signed as you, is at most 8 KB, and goes to the agent's inbox. It never goes into the terminal; the agent is sent the same one-line notice as for any message, when it is idle. Each message shows two marks: whether its recipient has read it, and whether you have seen it. Mark seen sets only your own mark and the count on the tab; the agent's inbox and its unread count are unchanged.

The panel works on the machine Flockdeck runs on. A window reached through the relay is refused its commands. A board of more than 300 open tasks lists the newest 300, with a button for the rest.

Routing

Helpers multiply whatever their model costs, and many of their tasks are mechanical: run the tests, rename a symbol, fix a typo. Routing pre-sets the model of a helper an agent starts with flockdeck spawn, and of the first prompt you send a pane, to one suited to the work (a smaller one for mechanical work, a stronger one for hard work). It is off until you turn it on, in Settings › Routing, for every project or for one.

A pane a rule routed says so in its header (claude · haiku ↘), with the rule, and the agent and model it would otherwise have used, in its tooltip. A pane Minimise cost routed with no rule runs the cheaper model without the arrow.

Routing moves work between the models of the agent the run is on, and only between models whose tier it knows. It sends work to another agent only when you turn on Let a rule send work to another agent, in the same place, and a rule names that agent's model and agent. A rule like that could send test runs to a cheaper agent, say. Even then, only a new helper moves, never a conversation already under way. The other agent has to be installed and trusted for the project. The pane header's tooltip names the agent and model it would otherwise have used. Claude Code's Default is whatever the CLI is set to, which might be its smallest model or its largest, so routing leaves work on it alone: make a model your default, for routing to choose from it.

Automatic routes a helper an agent starts with flockdeck spawn without -agent or -model, and the first prompt you send a pane from the prompt bar, while it has no conversation yet: the pane restarts on the chosen model with that prompt, and never on another agent. Never go below keeps routing off the smaller tiers for a project where the work matters.

Strategy decides what happens to a task no rule matches. Cost-first, quality-aware (the default) leaves it exactly where it was, the same as routing off would. Minimise cost routes it too, to the cheapest model Never go below allows on the agent it was already going to run on, never to another agent. Either strategy, a rule that matches still decides first and Never go below still holds; the strategy only changes what happens when nothing matches. The pane's tooltip says "no rule matched" for a choice made this way, so it is never mistaken for a rule's own reason.

The policy is kept in agents.json, and only there, never in a file inside a repository, so a repository you clone cannot change what your key spends:

{
  "routing": {
    "mode": "auto",
    "floor": "",
    "strategy": "",
    "rules": [
      { "name": "run the tests", "tier": "small",
        "when": { "task": "^(re-?)?run (the |all )?(unit |integration )?tests?\\b" } },
      { "name": "schema changes", "tier": "top",
        "when": { "files": ["**/migrations/**", "**/*.sql"] } },
      { "name": "design work", "model": "opus", "agent": "claude",
        "when": { "task": "\\bdesign\\b" } }
    ]
  },
  "projects": {
    "C:\\code\\payments": { "routing": { "mode": "auto", "floor": "mid" } }
  }
}

Rules are tried in order and the first that matches decides; a task no rule matches is left alone under "strategy": "balanced" (the default, same as leaving strategy out), or routed to the cheapest model the floor allows under "strategy": "cost". Every condition in when must hold: task is a regular expression matched without regard to case; minWords and maxWords bound the task's length; files are globs matched against the paths the task names (** is any number of directories, and a glob with no / matches a file's name anywhere); kind is spawn or turn; agent is an agent's id. A rule asks for a tier, or for one agent's model. Leave rules out for the built-in ones, which Settings lists; "rules": [] means none. A project's own policy replaces the one for every project whole. A rule that cannot be used (a pattern that is not one, a tier that is not one) is named in the notice and skipped, and the rest still apply.

Two things an older version wrote still load, and do nothing. "mode": "suggest" filled in the Fan out dialog, which no longer exists, so it is read as "off" with a notice; set it to "auto" to have routing choose models. A rule whose kind is fanout is named in the notice and skipped. A "jev" key is ignored and left in the file as written.

Saving a default from a Flockdeck that has no routing (0.2.10 or older) writes a project's entry back without its routing, so a project's policy is lost that way.

Routing makes no request. It decides from these rules alone. The routed mark on a pane travels only as the rest of the pane's state does, to your own paired devices when Flockdeck Remote is on. Helpers and first prompts are not logged. An older version that routed fan-out rows kept its choices in routing.jsonl in the state directory (the last 10,000 lines, never the task), and nothing writes to it now. Settings still lists each rule beside how often that log shows it overridden, once it has decided at least once. Settings has Clear routing history, and to turn all of it off, set every project to Off. A file that does not parse is a notice in the interface and nothing worse: the built-in agents carry on, because a typo in a settings file is not a reason to be unable to start work.
